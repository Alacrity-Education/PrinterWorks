# WS2812 Reconstruction Dataset & Task Brief

## The problem

An STM8S001J3 oversamples a WS2812 data stream into RAM like a logic
analyzer (GPIO polled in a tight assembly loop), then dumps the raw
sample buffer. The task: given one raw capture, reconstruct the payload
bytes of the frame that was on the wire.

The dataset (`../data/captures.json`) holds 54 real captures: 18 test
patterns x 3 repetitions, each with the ground-truth payload attached
(used by `eval.py` for scoring only — decoders must not read it).

## Signal (transmitter side — exact, crystal-derived)

- WS2812 NZR, 800 kbps: bit period 1250 ns, T0H ~350 ns, T1H ~700 ns,
  generated by an RP2040 PIO. Jitter is negligible; treat as exact.
- Frame = HEADER `FF 00 AA 65` + 16-byte payload + TRAILER `9A 55 00 FF`,
  bytes MSB-first. After the frame the line stays low (latch).
- Before the frame the line idles low; capture starts at the frame's
  first rising edge.

## Sampler (receiver side — the messy part)

A 640-iteration assembly loop samples the GPIO 8 times per iteration
(slots 0..7), packing samples into bytes. `harness.linearize()` returns
chronological `(iteration, slot, level)` triples with the byte-layout
quirks already handled.

### Timing ground truth (measured, not documented!)

- The loop period measured against the crystal-exact signal is
  **~2507.3 ns** (`harness.LOOP_NS`), i.e. ~40.1 nominal CPU cycles —
  NOT the 37 cycles the original source comment claims. Roughly 2 WS2812
  bits per loop.
- Per-capture clock varies (HSI oscillator): observed loop period spread
  ~2507-2524 ns across captures (~0.7%). Within one capture the clock can
  also drift slowly ("clock stretching"). Do not hard-code one period —
  calibrate per capture (the header/trailer are designed for this).
- The 8 slots within a loop are NOT uniformly spaced. The documented
  cycle positions [1,5,9,13,17,21,27,32]/37 are provided scaled into ns
  as `meta["slot_offset_ns_estimate"]`, but since the real loop is ~40.1
  cycles there are ~3 unaccounted cycles somewhere in the loop —
  probably enlarging one or more inter-slot gaps (byte-boundary delay).
  There may also be small data-dependent timing shifts (the sampling
  instruction sequence differs by one cycle depending on the pin level).
  Treat slot offsets as calibratable unknowns; the known header/trailer
  bit patterns and the exact 1250 ns bit grid are your calibration
  sources.

### Known artifacts to handle

1. **Clock stretching / HSI variation** — the receiver clock is only
   nominally 16 MHz; scale and drift must be estimated per capture.
2. **Swallowed 0-bits** — T0H ~350 ns can fall entirely inside an
   inter-slot dead zone, producing zero high samples: the bit leaves no
   pulse, only a longer-than-expected low gap. The `zeros`, `lone1`,
   `msb1`, `edges` patterns stress this.
3. **Byte-boundary delays** — the enlarged inter-slot gaps near the end
   of each loop distort apparent pulse widths and positions with a beat
   period of ~2 bits (observed: apparent T1H alternating ~8 vs ~15
   nominal cycles when using the naive 37-cycle time base).
4. **Merged pulses** — consecutive 1-bits sometimes appear as one long
   high (~1.8 us) when the ~550 ns inter-bit low falls into a dead zone.
5. First high sample: the capture is edge-triggered, so sample (0,0) is
   guaranteed high (or very near the first rising edge).

## Interface

Write a module `approaches/<name>.py`:

```python
def decode(samples: list[tuple[int, int, int]], meta: dict) -> bytes | None:
    """samples: chronological (iteration, slot, level); return the 16
    payload bytes, or None if no frame found."""
```

Helpers in `harness.py`: `approx_time_ns`, `to_levels`, `high_pulses`
(all built on the *estimated* slot offsets — improve on them if you can).

## ADDENDUM — calibrated timing model (supersedes the estimates above)

The sampler timing was subsequently fitted to all 54 captures
(`approaches/dev_calibration/fitted_model.json`, 99.96 % sample
agreement; full details in `HSI_TEMPERATURE.md` "Calibrated model"):

- Loop = **exactly 40 cycles (2500.0 ns nominal)**; inter-sample gaps
  **[4, 5, 4, 4, 4, 6, 5, 8] cycles** (slot offsets 0, 250, 562.5,
  812.5, 1062.5, 1312.5, 1687.5, 2000 ns).
- **Data-dependent term**: a HIGH read at slot j adds w[j] =
  [0, -1, 0, +2, 0, 0, 0, +1] cycles to all later sample times (BTJT
  taken-path cost differs per site). Causal — computable from the
  capture itself while decoding.
- Effective pulse widths: T1H 752 ns, T0H 377 ns (wire values +2 ns).
- This unit's HSI: **ε ≈ -1.12 %** (slow); true per-capture spread only
  ±0.014 % — the "~0.7 % loop-period spread" above was an artifact of
  the naive 37-cycle time base. The ±7.5 % design envelope stands.
- End-of-loop gap = 505.7 ns after a LOW slot-7 read, 568.9 ns after a
  HIGH one — vs T1L ≈ 498 ns: the 1-bit merge mechanism, now exact.

## Evaluation

```
python3 eval.py approaches/<name>.py            # train split (reps 0,1)
python3 eval.py approaches/<name>.py --holdout  # holdout (rep 2)
python3 eval.py approaches/<name>.py --all
```

Target: maximize exact-match rate on the train split without regressing
the holdout. Rules: do not modify `harness.py`, `eval.py`, or the
dataset; do not read ground truth inside `decode()`; deterministic code
only (no RNG without a fixed seed).
